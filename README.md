# qec-primitives-benchmark

Hardware benchmarks of the primitive that quantum error correction is built on: **measure an
ancilla mid-circuit and feed the outcome forward**. Every benchmark is a small Ising Hamiltonian
whose terms are measured through ancillas inside a linear-ramp QAOA (LR-QAOA). How close the device
gets to the exact noiseless approximation ratio, as a function of depth, tells how well it runs
that primitive.

**Version 0.1** covers **1D chains**, with the triplet `(d1, a, d2)` as the `n_data = 2` case, on
**IBM Quantum** (Qiskit Runtime), **IQM Garnet/Emerald** (Amazon Braket through
`qiskit-braket-provider`), **Quantinuum Helios** (Guppy programs through Nexus) and **Aer**. Surface- and colour-code patches come next. They fit the same
interface (see *Extending*).

It generalises `benchmarking_ibm_auto.ipynb`, `benchmarking_iqm_auto.ipynb` and the chain circuits
of `benchmarking_ibm.ipynb` from the `Benchmarking-Mid-circuit-measurement` repository, and it reads
that repository's result files.

## Workflow

The notebooks in `notebooks/` wrap this sequence. Each has one configuration cell, with `SUBMIT = False`
by default, so nothing is sent until you flip it.

`SUBMIT = False` is not a no-op: `IBMBackend(..., local=True)` builds an Aer noise model from the
chosen device's **own current calibration** and runs the same transpiled circuits locally, so the whole
pipeline — and a realistic preview of the result — costs nothing. Such runs call themselves
`<device>_sim` and every result file carries `"simulated": true` with the noise model's provenance, so
they stay separate from hardware data in `data/` and in `load_results`.

**With no vendor account at all**, use `SimBackend` (`BACKEND_NAME = "noisy_simulator"` in the IBM
notebook): a synthetic heavy-hex chip with the same depolarizing noise on every qubit and coupler. Its
error rates are arguments, not notebook knobs — defaults in `qecbench/noise.py`, overridden per run,
e.g. `SimBackend(p_2q=0.01)` or `SimBackend(qubits=27, topology="grid")`.

```python
from qecbench import Direct
from qecbench.backends import IBMBackend          # or IQMBackend("iqm_garnet"), AerBackend(graph)
from qecbench.layout import select_chains
from qecbench.experiment import build_plan, print_plan, submit, harvest
from qecbench.analysis import load_results

backend   = IBMBackend("ibm_phoenix", account="mcm-primitives")
chains    = select_chains(backend.coupling_graph(), n_data=2)     # 2 = triplets, 3+ = chains
instances = chains + [Direct.from_chain(c) for c in chains]       # + the direct reference
plan      = build_plan(backend, instances, depths=[3, 6, 9, 12], shots=500)
print_plan(plan, backend)                                           # circuits, jobs, cost
manifest  = submit(plan, backend)                                   # sends (or simulates, for a local backend)
harvest(manifest, backend)                                          # data/results/... one file per instance/depth
results   = load_results("data/results", backend.name, kind="mcm")  # {Chain: {depth: {r, r_err, r_ideal, r_ovl, ...}}}
```

| notebook | what it does |
|---|---|
| `benchmark_ibm.ipynb` | triplets or chains on any IBM backend; section 8 reloads the earlier `ibm_phoenix` triplet campaign |
| `benchmark_iqm.ipynb` | triplets on Garnet/Emerald; `LOCAL = True` rehearses the exact IQM circuit on Aer |
| `benchmark_quantinuum.ipynb` | 1D chains of 20-50 spins on Helios-1 / Helios-1E with the parallel MCM program; quote in HQC, `λ_eff` per edge |
| `paper_figures.ipynb` | every device-data figure of the paper, redrawn from `data/` (see *Paper figures*) |
| `noise_study.ipynb` | not a benchmark: depolarizing simulation of 1D chains giving `κ_r = κ_0/N_q`, `κ_ρ` and device `λ_eff` (see *Noise study*) |

The notebooks are generated by `notebooks/make_notebooks.py`. Edit that file and re-run it, either for all of
them or for the ones you name (`python notebooks/make_notebooks.py paper_figures.ipynb`), since
regenerating a notebook replaces any edits made to its `.ipynb`.

Outputs are filed by device, problem and implementation, so a long campaign stays navigable and the
code primitives will land beside the chains instead of in the same heap:

```
data/
  results/<backend>/<structure>/<kind>/<stamp>_<backend>_<structure>_<kind>.json
          e.g. ibm_phoenix/chain/mcm/…   ibm_phoenix/chain/direct/…   ibm_phoenix_sim/chain/mcm/…

```

`structure` is the problem (`chain` now, `surface_code` / `color_code` later) and `kind` the
implementation (`mcm` or `direct`), so a `Direct` reference sits next to the chain it is compared with.

**One file per run**, holding a `run` header (manifest, shots, depths, `simulated`, noise model) and a
`results` list with every instance and depth — a campaign that used to be hundreds of files is two.
Re-harvesting a manifest merges into the same file, so jobs finishing later are added rather than
duplicated. `load_results` reads run files, single-result files and a flat directory alike, so earlier
campaigns keep working untouched.

To fold older per-instance files into this layout:


## The circuit

One LR-QAOA layer for a term with ancilla `a` and data qubits `d_1..d_k`:

```
H_a  CZ(d_1,a) ... CZ(d_k,a)  RX_a(2γ)  measure a  ─┬─ if 1: Z on d_1..d_k, restore a to |0>
                                                     └─ then RX(−2β) on all data qubits
```

This is the same operation as `CX … CX · RZ(2γ) · H · measure` (the inner Hadamards of the CXs
cancel), i.e. `exp(−iγ Z…Z)` followed by the mixer. Both vendors run this same logical circuit:

* **IBM / Aer**: Qiskit `if_test`; transpiled with the layout pinned, and a plan with any routing gate is rejected.
* **IQM**: natives only (`H = R(π,0)R(π/2,π/2)`, `RX(t) = R(t,0)`, `Z = R(π,π/2)R(π,0)`, so each
  conditional Z is two `cc_prx`), with active reset by `cc_prx` on the ancilla, submitted verbatim
  inside `EnableExperimentalCapability`.

Two implementations of the **same** `n`-spin Hamiltonian, and the benchmark is the comparison
between them: a `Chain` (`n` data qubits + `n-1` ancillas) runs the gadget above, kind `mcm`, while
a `Direct` instance (`n` adjacent data qubits) applies each bond's rotation straight to its coupler,
`RZZ(2γ)`, with no ancilla, no measurement and no feed-forward, kind `direct`. Same Hamiltonian,
same depth, same noiseless reference, so their `r` compares directly; per layer and per bond, `mcm`
pays one extra mid-circuit measurement and its feed-forward.

`Direct.from_chain(chain)` builds that counterpart. It cannot reuse the chain's own data qubits —
those are two hops apart, with the ancilla between them — so it takes `n` adjacent qubits of the
same path, keeping it on the same patch of the chip: a triplet `(d1, a, d2)` gives the pair
`(d1, a)`. Both kinds go into the same jobs, so the gap between them is measured under one
calibration.

Result files written by other tools are still read whatever their kind (`load_results(..., kind=...)`),
including the `mcm_reset` variant of earlier campaigns, which restored the ancilla with a `reset`
instruction and is no longer built here.

The tests simulate both dialects on Aer and check them against the exact `r_ideal`, for a triplet
and a 3-spin chain in the same circuit.

## Device rules that shape the experiment

* **Quantinuum Helios, logical chains.** Helios is all-to-all and reuses qubits, so there is no
  layout: `chain_instances(n)` gives data qubits `0..n-1` and ancilla labels `n..2n-2`, and one
  program runs one chain. MCM programs use the **parallel ordering** (`qaoa_mcm_parallel`). Each
  layer runs the even bonds, then the odd bonds, with each class's ancillas allocated together and
  read by one `measure_array`. No gadget then waits on its neighbour, although at most 8 run at once
  (Helios-1's operation zones), so a class of `k` gadgets takes about `ceil(k/8)` steps. A program
  holds `n + ceil((n-1)/2)` qubits at once (at most 98), which is also what a Helios-1E emulator job
  is sized to. The direct program is `CX RZ CX` per bond. Cost
  is quoted by Nexus in HQCs (`backend.quote(plan)`) and sets each job's `max_cost`. `local=True`
  runs a gate-for-gate Qiskit copy of the program on Aer.

* **IQM, one controller per qubit per circuit.** In `d0-a0-d1-a1-d2` the middle data qubit would be
  corrected by both `a0` and `a1`, which Braket forbids. On IQM the MCM gadget therefore runs on
  **triplets only**. For longer chains `build_plan` rejects the `mcm` kind with that explanation, and
  `Direct` instances have no feed-forward and run at any length.
* **IQM feed-forward groups.** Control only inside a group. `restrict_to_groups` removes the
  couplers between groups before instances are selected.
* **IBM, classical-control memory** (error 6073). Circuits per job are capped (`max_circuits_per_job`, default 8).
* **IBM cost estimate.** Feed-forward is charged 1.9 µs per conditional per layer. That figure is an
  *unconfirmed hypothesis* carried over from `ibm_mcm_auto`, so treat the QPU seconds as an order of magnitude.

## Analysis conventions

* `r = (E − E_max)/(E_opt − E_max)`. Bitstring character `i` is data qubit `i`, and the spin is `1 − 2x`.
* `r_rand` and its shot-noise σ are **exact** for the uniform distribution (1/2 for chains). The
  legacy seeded bootstrap gave 0.506 ± 0.020 for 500-shot triplets.
* `r_ideal(p)` comes from an exact statevector. `r_ovl = (r − r_rand)/(r_ideal − r_rand)`: 1 is
  noiseless, 0 is random.
* Result files keep the `utils.save_experiment_results` schema and add a `benchmark` block. File
  names: `<stamp>_<backend>_chain_<qubits>_<kind>_nq<n>_depth<p>.json`.
* `load_results` also reads the legacy `*_tri_<d1>_<a>_<d2>_*` files and recomputes everything from their samples.

## Noise study

`qecbench.noise_study` supports the step that turns overlaps into an effective error rate. Put a
two-qubit depolarizing channel of strength `λ` after every **edge interaction** (one `exp(−iγ Z_i Z_j)` per
edge per layer) of an `N_q`-spin chain at depth `p`. Every overlap then falls on `2^(−κ ε_acc)` with
`ε_acc = N_edges · p · λ` (`N_edges = N_q − 1`), where `κ_r = κ_0/N_q` for the approximation ratio and
`κ_ρ ≈ 1` for the probability of the optimum. With `κ` held fixed, a device's overlaps give `λ_eff`.

`λ` is counted per edge, not per gate, so the implementation stays out of the model. The direct circuit
spends two CNOTs on an edge. The MCM circuit spends CZs, an ancilla measurement and feed-forward. Both get
a `λ_eff` in the same unit, and their ratio is what an edge costs through MCM relative to CNOTs. A
channel of strength `λ_CX` after each CNOT is exactly `λ = 1 − (1 − λ_CX)²` per edge (`lambda_from_cx`).

It uses no density matrix. Carrying each Pauli fault forward as a sign flip of later angles, and splitting
by the number of faults `k`, reduce the problem to pure-state runs. One set of runs per `(N_q, p)` gives
the overlap at every `λ`. On a laptop, `N_q = 5…15` at `p = 2, 5, 10` takes about 100 s. The tests check
it against Aer's density matrix to 1e-12.

```python
from qecbench.noise_study import run_study, collapse, fit_kappa, fit_kappa0
decays = run_study(range(5, 16), [2, 5, 10], cache="data/noise_study/chain_depolarizing.json")
fits   = {n: fit_kappa(*collapse(decays, n, lambdas, "r")[:2]) for n in range(5, 16)}
```

Results so far: `κ_0 = 3.69 ± 0.01`. `κ_ρ` drifts with depth, 0.95 over `p ≤ 10` and 1.02 over
`p = 10…50`, so it is fitted at the depths a device actually ran. The device runs are converted into
`data/results/` (`ibm_boston` and `Helios-1E`, `N_q = 10`), so the notebook needs nothing outside this repository.
`λ_eff` per edge (from `r`) for the 10-spin chain: `ibm_boston` direct 1.08e-2 and MCM 1.66e-2 (×1.54);
`Helios-1E` (Quantinuum's emulator) direct 2.12e-3 and MCM 2.68e-3 (×1.26).

The fit extends to chains longer than can be simulated, assuming `κ_r = κ_0/N_q` still holds there.
Section 7 of the notebook redraws `λ_eff` per edge against `N_q = 10…60` for eight devices (IBM boston,
pittsburgh, kingston, fez, marrakesh and phoenix, Quantinuum Helios-1 and H2), direct and MCM. It fits
their runs with the same windows as the published figure. Because every reference is exact and
`κ_0 = 3.69`, the 1000-shot IBM values come out 0.95× the published ones (the ratio of the two `κ_0`),
and runs with fewer shots move by up to about 12%.

Those runs, 530 files of `Benchmarking-Mid-circuit-measurement/Data`, are converted into 40 run files
under `data/results/<backend>/chain/<direct|mcm>/` with

```bash
python scripts/import_legacy_chains.py "../Benchmarking-Mid-circuit-measurement/Data/<stamp>_<backend>_1dpin_MCM_nq*" --apply
```

It reads `<stamp>_<backend>_[1d|1dpin|1dfix|1dfree_]<normal|MCM>_nq<n>_depth<p>.json`, files `normal` as
`direct` and `MCM` as `mcm`, and recomputes `r`, the exact references and `r_ovl` from the samples. Chains
whose device reused ancillas get logical ancilla labels. The noiseless reference of an open chain is
computed exactly as free fermions (`lrqaoa.chain_energy_free_fermions`), in milliseconds even at 120 spins
and depth 50.

## Extending

A new primitive family is a `Primitive` subclass that defines `data_qubits` and `terms`
(`Term(ancilla, data)`), plus `optimal_energy` / `max_energy` if brute force is too slow. Circuit
builders, packing, validation, submission and analysis work from the terms, so a surface-code
plaquette is `Term(a, (d1, d2, d3, d4))`. What a new family still needs is its own instance search
in `layout.py`, the analogue of `select_chains`. On IQM the single-controller rule applies to it as well.

A new vendor is one `Backend` subclass: `coupling_graph`, `validate`, `build`, `estimate`, `submit`, `fetch`.
